People

Contacts dashboard

A contacts dashboard that turns a messy address book from .vcf, Excel, CSV or Google Contacts into one clean, searchable list, grouped into circles, with reminders to keep in touch. It runs entirely in the browser.

Read the People case study
Problem
Contacts end up scattered across a phone, a Google account and old spreadsheets. My own contacts lived in an .xlsx file, and no tool made it easy to clean them up and remember to stay in touch.
Users
People who manage a lot of relationships, like client-facing staff and coordinators, who want one tidy list without signing up for a CRM.
My role
Defined the problem from my own use, designed the flow and the landing page, built it with AI-assisted development and deployed it on Vercel.
Solution
Import from .vcf, .xlsx, .csv or Google Contacts, then see one cleaned list. Group people into circles, mark favourites, set a keep-in-touch reminder, write private notes, search, and export the clean list back out as a vCard. The dashboard greets you by name.
Built with
A single-page HTML, CSS and JavaScript app. Google sign-in with the People API, read-only contacts scope. vCard, Excel and CSV parsing in the browser. Data saved in browser storage. Hosted on Vercel.
Decisions
Local-first storage, so no contact data is sent to a server I run. Read-only Google access, so the app can never change someone's real contacts. Spreadsheet columns are matched automatically, so a group or category column becomes a circle and carries over on export.
Challenges
Real spreadsheets are messy: odd column names, missing country codes and duplicates. The importer guesses columns by name and explains that adding a country code such as +91 helps catch duplicates.
Limits
Contacts live in one browser and do not sync between devices. Google import is one-way.
Evidence
Live and public. I'll add usage and feedback here once I have them.
Next
Optional account sync across devices, duplicate merging, and two-way Google sync.

SOP Builder

Plain language to SOPs

Describe a process the way you'd explain it to a new hire and get back a structured SOP with owners, steps and checks. My team already uses its share links to keep handovers consistent.

Read the SOP Builder case study
Problem
Teams explain processes out loud and in chat, so handovers depend on who remembers what. Writing proper SOPs takes time nobody has.
Users
Operations and service teams, team leads, and the new hires they hand work to.
My role
Came from my own process-management work. I defined the SOP format, wrote the prompt, designed and built the app, and put it in front of my own team first.
Solution
Describe a process in plain words, or start from an example. Claude returns a titled SOP with 5 to 9 ordered steps, an owner and time for each, critical steps flagged, a checklist, KPIs and an escalation rule. Save it to your library, download it as PDF or Word, copy it as text, or share a read-only link staff can tick through.
Built with
A Claude artifact using Claude for generation, a per-user saved library, jsPDF for PDF and JSZip for Word export.
Decisions
The model must reply in a fixed JSON shape, so every SOP renders the same way and can be exported. Staff get a read-only link rather than accounts, so a handover takes one tap. It stays a Claude artifact instead of a separate website, which keeps it simple to run.
Challenges
Model output is not always usable. Descriptions under six words are rejected before sending. Replies without a valid steps list are caught, and rate limits, refusals and cancelled requests each get a clear message instead of a broken page. A Stop button keeps the description so nothing is lost.
Limits
Building an SOP needs the page open in Claude. The saved library has a storage limit.
Evidence
My team uses its share links to keep handovers consistent.
Next
Test it with more teams, then add version history and team libraries.

Luxury Escapes

Trip requests on WhatsApp

A luxury travel webapp where guests browse destination cards, open an offer and send a trip request straight to WhatsApp. It started from a Bali getaway reference and is live on Vercel.

Read the Luxury Escapes case study
Problem
In luxury travel, enquiries arrive as scattered messages, and coordinators go back and forth to collect basic details before they can plan anything.
Users
Travellers planning a premium getaway, and the coordinator who receives their request.
My role
Drew on my work in luxury travel and concierge. I designed the journey from discovery to enquiry, built the app and deployed it from GitHub to Vercel.
Solution
Browse destination cards, open an offer, then fill in a short trip form: dates, days, guests, departure city, budget per person, trip style, occasion and special requests. Sending opens WhatsApp with the whole request written out, ready to send.
Built with
A single HTML file with vanilla JavaScript and WhatsApp click-to-chat links. Hosted on Vercel from GitHub.
Decisions
WhatsApp instead of a form backend, because that is where these clients already talk to their coordinator. The message is structured so the coordinator gets every detail in one go.
Challenges
A website cannot send a WhatsApp message by itself, so the page tells the guest clearly that they tap send in WhatsApp to deliver it.
Limits
No booking, payment or request tracking. Requests live in WhatsApp.
Evidence
Live, with trip requests going straight to my WhatsApp.
Next
Real availability and pricing per offer, and a simple log of incoming requests.

Mercury

AI trip planner

Describe your trip in a sentence and Mercury writes the full day-by-day itinerary, ready to download as a PDF. It stores nothing you type.

Read the Mercury case study
Problem
Planning a trip means stitching together tabs, blogs and notes before you even have a day-by-day plan.
Users
Travellers who want a complete first draft of an itinerary quickly, to refine or share.
My role
Built it with Lovable, from the user flow to the interface, and shared it on social media for feedback.
Solution
Enter your destination, dates and travel style. Mercury writes a complete day-by-day itinerary in one go, which you can download as a PDF.
Built with
Lovable (React) with a backend function that calls the AI model, so no key sits in the page. The PDF is generated in the browser with jsPDF.
Decisions
One-shot generation keeps the experience fast. Nothing you type is stored or shared; it is used only to write the itinerary.
Challenges
Vague requests produce generic plans, so the page asks for more detail up front: the more you share about the trip, the better the itinerary.
Limits
An AI-written itinerary is a draft. Opening hours, prices and travel times should be checked before booking.
Evidence
Live and shared publicly for feedback.
Next
Editing single days without regenerating everything, and live checks on opening hours and travel times.
